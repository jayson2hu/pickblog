CodePick L3 应用与分发 - 架构设计

本设计约束 L3 只做应用与分发，隔离内部用户服务和外部公开服务，并通过可替换 Provider 支持独立开发与最后联调。

1. 服务拓扑

Next.js Reader Web
  -> reader-api /api/*       JWT, user context, Pro gate
  -> public-api /v1/*        API Key, quota, public field filter
  -> mcp-server tools        same public filter as /v1

reader-api / workers / public-api
  -> ContentReadProvider     Stub by default, L2 HTTP in integration
  -> L3Repository            in-memory dev or SQLAlchemy/PostgreSQL
  -> BillingClient           sandbox by default, Paddle in production
  -> EmailClient             mock by default, Resend/SES in production

2. 信任边界

边界鉴权可见数据禁止事项
内部 /apiJWT用户资料、兴趣、关注、收藏、个人早报、伴读不得用 API Key 进入用户态
外部 /v1X-API-Key + RPM + 日配额裁剪后的公开内容、分数、来源、垂类不得泄漏推荐决策、隐私上下文、完整分析、翻译对象
MCP工具进程边界与 /v1 同一公开字段集合不得绕过 Public API 的字段过滤语义

3. 领域模块

模块职责当前路径
Provider封装 L2 读取契约，提供 stub 和 HTTP 实现services/shared/codepick_l3/provider.py
Auth / GateJWT、当前用户解析、集中 require_planauth.py, gating.py
RepositoryL3 自有状态持久化接口、内存实现、SQLAlchemy 实现repository.py
Billing沙箱 checkout、Paddle checkout、webhook 验签billing.py
Briefs / Workers公共与个人早报生成、持久化、邮件投递、Arq 配置briefs.py, workers/briefs/jobs.py
UsagePublic API API Key、RPM、日配额usage.py

4. L3 表归属

L3 只拥有以下表，并通过 Alembic 迁移维护：

users
subscriptions
user_interests
user_follows
reading_events
briefs
bookmarks
api_keys
api_usage_daily
companion_usage

L0-L2 内容、评分、翻译表只读且不在 L3 迁移中创建。

5. 运行时切换

场景配置期望
独立开发L3_USE_STUB_L2=true, BILLING_ENVIRONMENT=sandbox, EMAIL_PROVIDER=mock无真实 L2、支付、邮件账户也能跑通 smoke 和 E2E
L2 联调L3_USE_STUB_L2=false, L2_BASE_URL, L2_API_KEY仅 Provider 层切换，业务入口不改代码
生产支付BILLING_ENVIRONMENT=production, PADDLE_CHECKOUT_BASE_URLcheckout URL 走 Paddle，webhook 仍验签后更新订阅
邮件投递EMAIL_PROVIDER=resend 或 ses个人早报投递使用真实 provider 配置

6. 验证策略

  • 后端 pytest 覆盖鉴权、门禁、配额、webhook 验签、L2 切换、SQLAlchemy 状态、MCP 裁剪和价格币种。
  • scripts/l3_smoke.py 作为 Sprint smoke，成功输出 L3 PIPELINE: PASS。
  • Reader Web 使用 Playwright 覆盖双语展示、详情 SEO、早报门禁、登录、本地伴读和沙箱结账。
  • CI 分 backend 与 reader-web 两个 job 执行 smoke、typecheck 和 E2E。
